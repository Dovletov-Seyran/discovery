# Санджар: предметы и интерактив воскресного ТЗ

Ветка `sanjar`, PR в `main` без автоматического слияния. Основа — `main` `99e9e83`.
Пользователь передал Санджару также связанные задачи Кирилла: переворот часов, петли дверей/крышек и рендер `world_patch`.

## Что реализовано

- Меч перенесён на бочку у борта, ром — к припасам и вину. Карта и компас остаются в навигационной части. Раздел `npcs` не менялся.
- Выносливость занимает компактный блок по содержимому с переносом на узком экране.
- ЛКМ использует предмет и без цели; первый клик также работает до захвата мыши. F включает бросок следующим ЛКМ, повторное F отменяет; G ставит предмет на поверхность под прицелом. Меню и чат сбрасывают режим броска.
- Песок верхней колбы убывает, нижняя наполняется, струя исчезает в конце; переворот длится 650 мс. Сервер передаёт `startedAt`, `duration` и `emptyAt`, поэтому поздний вход не запускает полный таймер заново. Убраны два конкурирующих обновления заполнения.
- Предметы можно положить, бросить и снова подобрать. Сервер проверяет владение, расстояние, координаты, скорость, поверхность и коллизии. Остаток порций сохраняется. Одновременный/повторный подбор не создаёт копий. Однотипные предметы не складываются: существующая модель инвентаря хранит порции по типу.
- На E открываются крышки обоих корабельных сундуков и входные двери домов, дома губернатора и склада. Дома имеют проёмы и пол, а не сплошную коробку. Створки блокируют проход в закрытом состоянии. Сервер не закрывает дверь, если в ней стоит игрок. Состояния сохраняются и восстанавливаются.
- Физика использует ограничивающие сферы, шаг 1/120 с, гравитацию, отскок и трение. Коллайдеры берутся из тех же процедурных моделей, что у клиента; новых физических библиотек нет. Сервер задаёт время старта, клиенты считают полёт, сервер присылает контрольные положения и окончательную остановку. Недостающий чанк приостанавливает клиентский прогноз до загрузки; серверная коррекция остаётся источником истины.
- Деревянная кружка и пустой бочонок на палубе, а также брошенные кружки/пустые бочонки реагируют на общий расчёт крена. Защита от потери квестового предмета возвращает упавший в море предмет к безопасной поверхности рядом с местом броска.
- Патчи `spawn/remove/set` создают, перемещают, скрывают и удаляют объекты; новые предметы попадают в raycast и подбираются. Состояния повторно применяются после загрузки чанка. Изменения положения уже существующей двери сохраняют её локальную систему координат.
- Сервер рассылает предметные `world_event`: `eat`, `drink`, `throw`, `swing`; выстрел — `scare`. Клиентский произвольный `world_event` не принимается.

## Стыки для команды

### Тамерлан

`shared/protocol.js` содержит `PLACE`, `THROW`, `TOGGLE`, `WORLD_PATCH`, `WORLD_EVENT`.
Единая функция отправки событий — `emitWorldEvent(player, type, extra)` из `server/game/world-events.js`.
Она поддерживает весь список типов из ТЗ, включая добавленный `throw`; предметные действия уже подключены.
Её можно вызывать для своих `talk`, `run`, `scare`, `dance`, не добавляя вторую рассылку предметных событий.
Админка и её метрики остаются отдельной задачей.

### Сейран

Для появляющихся подбираемых предметов использовать серверные функции из `server/game/objects.js`:

```js
spawnWorldItem({id:'ration:<scene-run>:0', zone:'ship', item:'biscuit', p:[1, .9, -3]});
setWorldObject(id, {p:[2, .9, -3]});
removeWorldObject(id);
```

`spawnWorldItem()` регистрирует предмет до рассылки патча, проверяет тип и координаты, сохраняет состояние. ID должен быть уникальным: повторный spawn существующего ID отклоняется. `p` — точка основания модели в мировой системе координат. Порции можно передать полем `uses`; иначе берётся стандартное количество. Для изменения непредметного состояния доступны `entities.setState()` и `syncAll()`; конкретные эффекты тумана/флага/парусов требуют своего согласованного обработчика, здесь они не реализованы.

### Кирилл

`world.applyPatch({ops,serverNow})` уже подключён через `WorldConnection`.
Входные двери имеют ID `<building-id>:door:0`, сундуки — `nav_chest` и `arms_chest`.
Песок, переворот, крышки и входные створки реализованы в этой ветке. Основные точки подключения: `world/objects.js`, `world/props.js`, `world/islandModels.js`.

## Формат состояния и ограничения

- В запросах `place` и `throw` поле `p` — центр физической сферы. В `world_patch` и `entity.state.p` — основание модели. `state.body.p` — центр сферы для расчёта полёта; `state.body.v`, `startedAt`, `step` передают согласованную точку продолжения.
- Полёт ограничен восемью секундами; одновременно не более 16 активных тел. Крен продолжает двигать лёгкие перекатывающиеся предметы после этого интервала.
- Не более 96 динамических определений на сервере, клиент получает до 24 ближайших динамических объектов своей области. Повторный снимок раз в две секунды позволяет восстановить локально вытесненные предметы.
- Состояния патчей учитываются в том же лимите 10% данных мира. Локальный реестр ограничен 16 КБ и доступным остатком бюджета; дальние записи вытесняются первыми, у острова резервируется место под рельеф.
- Серверный кеш геометрии ограничен 64 чанками; шаблон коллайдера модели строится один раз. На клиенте используются уже загруженные коллайдеры.
- Баланс денег остаётся свойством игрока: перекладывание кошелька не переводит деньги другому игроку.

## Проверки

Итог текущей реализации: 121 тест прошёл, один пропущен; production-сборка успешна. Проверка двух авторизованных WebSocket-клиентов прошла на отдельном сервере с тестовой БД.

- Автоматические проверки включают разные частоты кадров, отскок/трение, крен, коллизии проёмов, часы при позднем входе, петли после объединения геометрии, подбор, порции, сохранение/восстановление, проверки сервера и квоту кеша.
- `server/scripts/smoke-objects.js` предназначен только для отдельного `DEV=1` сервера с одноразовой БД. Он регистрирует двух тестовых пользователей, сбрасывает тестовый прогресс, меняет сцену, выдаёт предметы и проверяет реальный WebSocket-обмен. Обычную игровую БД для него использовать нельзя.
- Графическая проверка в браузере пока не выполнена: встроенная вкладка не подключилась. Проверки геометрии и состояния выполнялись в Node.js; окончательный внешний вид нужно посмотреть в игре.
